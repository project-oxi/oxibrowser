# OxiBrowser 1차 목표: 일반 SPA 동작과 검증 설계

작성일: 2026-10-27. 근거: [기능·호환성·성능 진단](2026-10-27-capability-baseline.md)과 [재현 증거](2026-10-27-capability-evidence.json). 진단한 엔진 리비전은 `edee0cfee8bd95f2144b63f34be2b22e4ac2c69e`다.

## 목표와 결정 상태

**확정된 목표:** 일반적인 상태 기반 SPA에서 사용자가 페이지를 열고 조작하면, 애플리케이션이 정상적으로 상태를 변경하고 결과를 화면에 표시하며 자동화 클라이언트가 그 결과를 확인할 수 있다.

아래 대표 작업, 통과 기준, 구조와 순서는 이 목표를 실현하기 위한 설계다. **2026-10-30 소유자가 이 설계를 바탕으로 구현을 지시했다.** 버전 후보는 초기 검증 대상으로 채택하며, 현재 지원 결과는 실제 테스트로 따로 기록한다. 기존의 Rust/Boa/Blitz 구조 및 Chromium/V8을 내장하지 않는 원칙을 유지한다. Chrome은 별도 실행하는 비교 대상이다.

### 범위

1차 지원 대상은 HTML/CSS, JavaScript 모듈, Fetch, 타이머, DOM 이벤트, 폼, 라우팅 및 기본 스토리지를 사용하는 데스크톱 웹 SPA다. 작은 예제뿐 아니라 비동기 요청, 라우팅 및 실제 사용자 입력을 포함한 앱을 대상으로 한다. 로그인 제공자, 타사 서버나 실제 계정에 의존하지 않고 로컬 서버와 고정된 데이터로 검증한다.

프레임워크별 전체 지원을 선언하지 않는다. 아래에 고정한 버전과 작업을 통과했을 때만 해당 조합을 검증했다고 말한다. Canvas/WebGL 게임, 미디어, Worker/Service Worker, 광범위한 IndexedDB 트랜잭션, Web Crypto 전체, WebGPU, 완전한 브라우저 확장 및 전체 CDP는 별도 범위다. 1차 대상 앱에 그 기능이 실제 필수라는 근거가 발견되면 범위를 다시 결정한다. 기존에 동작하는 기능과 보안 정책을 제거하는 뜻은 아니다.

## 완료 판정: 대표 작업

모든 작업은 동일한 고정 fixture를 별도의 Chrome과 OxiBrowser에서 실행한다. 초기 실행은 macOS에서 기존 진단과 같은 Chrome `156.0.8078.48`을 비교 기준으로 삼고, 실행 파일·OS·빌드 옵션·버전을 결과에 기록한다. CI에서 그 버전을 항상 사용할 수 있다는 전제는 두지 않는다. 기준 브라우저와 각 fixture 및 의존성 버전은 테스트 자산에 고정하고, 업그레이드는 별도 변경으로 비교한다. React `18.2.0`, Vue `3.5.13`, Playwright `1.48.2`를 초기 고정 후보로 제안한다. 이 버전들이 현재 지원된다는 뜻은 아니다. 로컬 fixture의 서버와 자산은 의존성 고정·해시 검증 및 라이선스 확인을 거쳐 마련한다.

| 작업 | 수행과 통과 조건 |
| --- | --- |
| 일반 폼과 이벤트 | HTML을 열고 실제 자동화 입력으로 텍스트 입력, 포커스 이동, 필수값 오류, 체크박스 선택, 제출을 수행한다. 값, `activeElement`, 이벤트 순서, 유효성 결과와 화면에 표시된 제출 결과가 기대값과 일치한다. capture → target → bubble, `once` 및 전파 중단을 별도 회귀 케이스로 확인한다. |
| React 상태 변경 | React 18.2 카운터와 폼이 초기 표시된다. 클릭·키 입력으로 상태가 변하고, 리스트 추가·삭제 및 조건부 표시 후 DOM과 화면 결과가 일치한다. 같은 노드 재조회와 프레임워크의 노드 소유 상태가 유지된다. |
| Vue 상태 변경 | Vue 3.5.13으로 구성한 별도 앱에서 입력 바인딩, 리스트 변경, 조건부 표시와 이벤트 처리를 확인한다. React 예제의 결과를 Vue 지원의 대리 지표로 사용하지 않는다. |
| 비동기 데이터와 경로 | 앱이 로컬 JSON을 Fetch해 로딩·성공·오류 화면을 표시한다. 앱 내부 링크, 뒤로/앞으로, 직접 경로 진입, 새로고침을 거쳐 URL과 내용이 일치한다. 경로 전환 때 지연 로딩된 모듈과 스타일시트가 적용되고 로드/오류가 정확히 보고된다. |
| 저장과 재방문 | 독립 프로필에서 설정을 바꾸고 새로고침·재방문한 후 localStorage의 값과 UI가 유지된다. 다른 브라우저 컨텍스트에는 그 값이 나타나지 않는다. |
| 같은 출처 iframe | 부모가 child의 `contentWindow`/`contentDocument`에 접근하고 child의 텍스트·버튼을 확인한다. child 입력과 부모의 결과 표시가 동작하며 페이지 교체 후 오래된 참조가 새 문서를 가리키지 않는다. 교차 출처 접근은 허용하지 않는다. |
| 화면과 좌표 | 중첩 여백, 스크롤, 스타일 변경이 있는 요소에서 computed style·viewport 기준 사각형·히트 테스트·캡처한 화면이 같은 상태를 나타낸다. 각 fixture의 예상 좌표와 주요 색상/박스 영역을 검사한다. 스크린샷 전체의 픽셀 동일성은 요구하지 않는다. |

실제 사용자 경로의 클릭·타이핑·포커스는 Playwright의 입력 API를 통해 검증한다. `evaluate`는 DOM/상태 관찰 및 별도 API 회귀 테스트에 쓸 수 있지만, 사용자 입력의 대체물로 사용하지 않는다. 클릭 성공은 명령의 성공 응답이 아니라 **대상 이벤트, 상태 변경 및 화면 결과**까지 확인한다. 기존 CDP의 객체 참조 등 부족한 부분은 선택한 클라이언트 동작을 실제로 실행해 필요한 범위를 확정한다. 지원하지 않는 CDP 명령이 성공한 것처럼 응답하는 것은 통과가 아니다.

### 공통 통과 규칙

- 기준 Chrome에서 먼저 모든 fixture가 정해진 결과에 도달해야 한다. 기준 환경 실패는 OxiBrowser 합격이 아니라 테스트 무효다.
- 기본 `serve` 설정의 OxiBrowser에서 각 전체 작업을 **새 프로세스와 새 컨텍스트로 10회 연속** 성공한다. 서버·fixture·설정은 각 실행에서 동일하게 유지한다. background 옵션 전용 성공은 기본 동작의 통과로 간주하지 않는다. MCP는 별도 실행 모드이므로 같은 작업을 사용할 수 있는 범위와 충돌을 따로 명시한다.
- 페이지 로딩부터 마지막 확인까지 예기치 않은 JS 예외, 실패한 필수 리소스, 프로세스 종료, 타임아웃이 없어야 한다. 테스트는 이 오류들을 수집하며, 예상한 오류 화면 테스트는 허용된 실패 요청을 명시한다.
- 각 수행은 상한 30초를 둔다. 이는 무한 대기를 막기 위한 **테스트 타임아웃**이며 사용자 경험에 대한 성능 목표가 아니다. 타임아웃이나 무한 재시도는 실패로 기록한다.
- DOM 값만으로 완료 판정하지 않는다. 해당 작업의 주요 요소가 실제 화면 캡처에도 표시되며, 좌표를 사용한 입력이 그 요소에 도달해야 한다. 화면 캡처는 동일 viewport·기기 배율·폰트 조건으로 비교한다.
- 10회 중 한 번이라도 실패하면 실패한 실행의 입력, 시각, 예외, 네트워크, 화면과 빌드 정보를 보존하고 통과로 처리하지 않는다. 재시도 결과는 별도로 기록한다.
- 완료는 고정된 fixture 전체, 아래 공통 불변식, 기존 회귀 및 제품 빌드에 대한 CI 게이트가 모두 충족된 경우에만 선언한다. 특정 fixture를 통과해도 임의의 SPA를 지원한다고 일반화하지 않는다.

### 공통 불변식

1. 같은 realm에서 같은 문서의 동일 노드를 어떤 DOM 경로로 찾아도 동일한 JS 객체이며 expando와 리스너가 유지된다. 분리 후 재삽입도 확인한다. 서로 다른 realm·문서의 수명과 격리는 별도로 시험한다.
2. `window`·`self`·`globalThis`, DOM 생성자와 프로토타입, `instanceof`가 1차 fixture에 필요한 Window/DOM 계약을 충족한다. 단일 생성자를 추가한 것으로 프레임워크 전체 호환성을 선언하지 않는다.
3. 실제 사용자 입력과 스크립트 이벤트는 capture/target/bubble, 취소, 기본 동작, 포커스 및 폼 상태를 일관되게 반영한다. JS 예외는 관측 가능해야 한다.
4. style 변경 이후 computed style, geometry, 입력 대상 및 캡처는 같은 페이지 상태를 본다. 좌표는 viewport 기준이며 스크롤과 부모 오프셋을 반영한다.
5. 페이지가 자동화 명령을 기다리는 동안에도 Promise, 타이머, 네트워크 완료 및 리소스 로딩이 계속 진행한다. 한 번의 `evaluate` 제한이나 한 문서의 교체가 다른 유효 작업을 잃거나 다른 컨텍스트를 오염시키지 않는다.
6. 지원하지 않는 기능을 성공 또는 동작 가능한 기능으로 잘못 보고하지 않는다. 부분 지원은 구체적 계약과 실패 방식을 문서화하고 fixture에서 검증한다.

## 성능과 안정성: 측정 계약

정확성이 통과한 실행만 성공 시간 통계에 넣고, 실패율·타임아웃은 별도로 함께 보고한다. 아직 성공하는 SPA 기준선이 없으므로 아래의 절대 지연·메모리 예산은 정하지 않는다. **성능 수치 목표는 동일 조건의 첫 성공 기준선 수집 후 별도로 결정한다.**

- 조건: CPU/메모리·OS, 브라우저 버전 및 빌드 기능, 명령행, viewport/배율, fixture 해시, 네트워크 조건, 캐시 상태, 측정 도구를 기록한다. 먼저 로컬 서버·기록된 warm-cache 조건을 기준으로 하고 cold-cache는 별도 실험으로 분리한다.
- 시간: 프로세스 시작→첫 준비 완료, navigation 시작→각 리소스/화면 준비, 실제 입력 전달→요구된 상태 변경 및 화면 갱신을 구간별로 측정한다. 실행 수와 p50/p95 및 실패 수를 함께 공개한다. 단, 표본이 적은 p95는 잠정치로 표시한다.
- 자원: 프로세스별 및 하위 프로세스를 합한 RSS 측정 가능 여부를 명시하고, 시작 직후·작업 완료 직후·반복 내비게이션 후의 메모리와 최대치를 구분한다. 바이너리 크기와 feature 조합도 기록한다.
- 안정성: 한 프로세스에서 작업과 내비게이션을 100회 반복하고, 독립 컨텍스트 2개를 함께 실행해 결과 격리·오류·메모리 변화를 기록한다. 전부 성공해야 하며 메모리 증가의 수치 허용치는 최초 기준선 수집 후 결정한다. 100회/2개는 초기 제안이며 실제 제품의 최대 부하 주장과 다르다.
- 병목: 각 구간에서 JS 작업·네트워크·스타일/레이아웃·캡처 비용을 구분할 수 있는 최소 계측을 설계한다. 현재 CDP Tracing의 메타데이터 출력만으로 구간별 비용을 추론하지 않는다. 실패한 작업의 빠른 종료를 성능 개선으로 집계하지 않는다.

## 설계안

### 1. 문서·realm에 귀속되는 DOM 객체

현재 [요소 객체 생성 경로](../../crates/oxibrowser-core/src/js/runtime.rs)는 같은 노드에 대해 새 wrapper를 만드는 경로가 많다. 문서와 JS realm이 소유하는 wrapper registry를 두고, DOM 조회·트리 이동·이벤트의 `target`/`currentTarget`·frame 접근이 같은 노드에 대해 같은 객체를 반환하도록 제안한다. 키에는 문서 세대와 노드 식별자를 포함해 내비게이션 뒤 식별자 재사용이 옛 객체를 새 노드에 연결하지 않게 한다.

분리된 노드는 JS 참조가 살아 있는 동안 계속 조작할 수 있어야 한다. 재삽입 시 같은 객체와 상태를 유지하며, 문서 교체·컨텍스트 종료·GC에서 오래된 객체와 리스너가 무한히 남지 않도록 수명 정책을 명시한다. Boa의 GC rooting/weak 참조 가능성과 스레드 제약을 먼저 검증해야 한다. 단순 전역 strong map은 메모리 누수와 문서 간 충돌 위험이 있다. registry는 해당 JS 스레드/realm 내부에 두고 Rust 쪽에는 안전한 식별자와 메시지만 넘긴다.

Window, Document, Element 및 구체적 HTML 요소의 생성자와 프로토타입을 realm별로 구성한다. 같은 출처 frame에는 해당 frame의 Window/Document를 연결하고, 교차 출처에는 접근 검사를 둔다. frame의 실행 컨텍스트가 이미 존재한다는 사실과 부모에서 접근 가능한 DOM 계약은 별개로 검증한다.

### 2. 이벤트·입력·상태

DOM 이벤트 경로를 문서 트리에서 구성한 뒤 capture → target → bubble 단계로 실행한다. `once`, 전파·기본 동작 취소, 리스너 제거 및 이벤트 중 DOM 변경을 명시적으로 시험한다. 자동화 입력을 이 경로와 공유하게 하고, 포커스 및 텍스트 입력·폼 상태·기본 동작의 순서를 관찰 가능한 계약으로 둔다. 리스너 오류는 브라우저 이벤트 처리의 연속성을 유지하면서 진단 채널에도 전달한다. `click()`에 의한 이벤트와 실제 포인터/키 입력의 차이는 별도 테스트한다.

### 3. 하나의 스타일·레이아웃 관측 계약

현재 [CSSOM](../../crates/oxibrowser-core/src/js/runtime.rs)과 [렌더 문서](../../crates/oxibrowser-render/src/document.rs)의 결과가 갈라진다. DOM 변경으로 스타일/레이아웃을 무효화하고, 필요한 읽기·입력·캡처 전에 동일한 문서 버전을 resolve하는 경계를 둔다. Stylo/Taffy의 실제 계산 결과를 computed style과 geometry의 근거로 공유하는 방안을 우선 검토한다. 레이아웃 좌표는 부모 변환·스크롤·viewport를 반영해 변환하고, 히트 테스트와 페인트도 같은 좌표계를 사용한다.

읽기마다 무조건 전체 렌더를 수행하지 않도록 dirty 범위와 resolve 시점을 계측한다. 폰트·리소스 도착, 동적 stylesheet와 DOM/스타일 변경 순서, 레이아웃 중 재진입, 스크롤 및 화면 배율은 별도 테스트한다. 픽셀 전부를 Chrome과 동일하게 만드는 일과 1차 업무의 필수 시각 정확도는 구분한다.

### 4. 자율 실행과 리소스 수명

현재 [작업 큐](../../crates/oxibrowser-core/src/js/job_queue.rs)와 background 옵션에 존재하는 제한을 전제로, 각 문서의 작업·microtask·타이머·네트워크/모듈 완료가 자동화 명령과 무관하게 진행되는 실행 모델을 설계한다. 타이머는 정확한 주기를 보장한다고 가정하지 않되 순서와 취소를 검증한다. 각 작업 뒤 microtask 처리 순서를 정하고, 긴 작업과 무한 루프에는 관측 가능한 제한 및 취소 경계를 둔다.

앱의 정상 작업과 자동화 `evaluate`의 제한을 구분한다. 네트워크·모듈 I/O가 JS 스레드를 막는 현 경로는 async 경계와 소유권을 설계해 해소 여부를 검증한다. 내비게이션·frame 제거·컨텍스트 종료 시 이전 문서의 콜백/네트워크 완료가 새 문서를 변경하지 않아야 한다. 기존 default serve와 MCP 설정의 충돌은 구현 전에 해소할 설계 선택지와 호환성 영향을 검토한다. 단순히 background 옵션을 켰다고 모든 실행 모드가 해결되는 것은 아니다.

### 5. 리소스와 자동화 계약

Fetch와 모듈 로딩은 실제 상태 및 바이트를 보존하고 성공/오류·취소를 전달한다. 동적으로 추가한 stylesheet는 요청, 적용, load/error 및 후속 스타일 계산까지 하나의 수명으로 관리한다. History API, 직접 경로 진입 및 localStorage는 fixture에 필요한 범위를 명시한다. 기존 egress/SSRF, origin 및 계정·자격 정보 정책을 유지한다.

Playwright 작업을 수행하는 데 필요한 CDP 메서드·이벤트·객체 참조와 해제 수명을 실제 클라이언트로 식별한다. 지원 범위 밖은 명시적인 오류 또는 문서화된 제한으로 처리하고 성공 응답만 보내는 기존 경로를 통과로 취급하지 않는다. CDP 전부를 1차 목표로 삼지는 않는다.

## 검증과 진행 순서

0. **측정 도구와 실패 재현:** 고정 fixture/서버, 독립 Chrome·OxiBrowser runner, 예외/네트워크/입력/캡처 수집과 판정기를 먼저 마련한다. 진단의 DOM identity, React 최초 실패, event, focus, CSSOM/좌표를 회귀로 옮긴다. 기존 텍스트 추출 corpus의 PASS와 분리한다. 이 단계는 이후 구현 계획이며 아직 실행하지 않았다.
1. **객체와 realm:** DOM identity·수명 및 Window/prototype/frame 기반을 해결하고 기준 불변식을 통과시킨다. 이후에도 React 전체 성공을 단정하지 않는다.
2. **입력과 자율 실행:** 이벤트·포커스·폼 및 이벤트 루프를 실제 사용자 작업과 함께 검증한다. 기존 background/MCP 동작을 회귀 검증한다.
3. **페이지 관측과 리소스:** CSSOM·좌표·페인트 일관성, 동적 리소스와 SPA 경로/Fetch를 검증한다. 서로 의존하는 문제는 단계 간 순서를 조정할 수 있으나 완료 판정은 전체 작업 기준이다.
4. **프레임워크·클라이언트:** React와 Vue 전체 작업, iframe·재방문 및 실제 Playwright CDP 경로를 통과시킨다. 실패가 드러나면 원인을 축소해 공통 불변식/표준 테스트에 추가한다.
5. **안정성·성능·배포:** 모든 작업에 대해 10회 신뢰성, 100회 내비게이션 및 2개 컨텍스트 결과를 기록한다. 성공 기준선을 수집하고 숫자 성능 목표를 정한다. CI는 최소 `browser` 배포 기능과 동일한 빌드를 대상으로 실행하고, 선택적 WebGL 등 다른 배포 profile은 별도 게이트로 취급한다.

단위 테스트는 수명·이벤트 순서·좌표 변환 등 원인을 빠르게 고립한다. 통합 테스트는 브라우저와 자동화 클라이언트 경계를 검증하고, 고정된 WPT의 관련 DOM/events/HTML/CSSOM 부분 집합은 출처·버전·선정 규칙과 기존 실패 목록을 기록해 추가한다. WPT 통과 개수를 1차 앱 전체 성공의 대체 지표로 쓰지 않는다. 보안·계정·추출 및 기존 WebGL 회귀는 관련 feature 조합에서 유지한다. 수정에 따른 병렬 GPU 문제는 기존 이력으로 따로 추적한다.

## 구현 전에 확정할 항목

- 위 React/Vue/Playwright 후보 버전, 대표 앱 작업과 같은 출처 iframe을 1차 필수 범위로 채택할지.
- 기본 `serve`와 MCP 각각의 자율 실행·호환성 계약 및 CLI 옵션 변경 정책. 두 모드의 동작을 시험하는 구체적 사용 경로가 필요하다.
- 성공 기준선 확보 후 지연 시간, 메모리, 장시간 안정성의 수치 예산과 이를 적용할 기준 하드웨어/운영체제. 현재는 측정 방식만 제안했다.
- wrapper 생명주기와 Boa GC 연동 방식, 공통 렌더 상태 노출 API 및 실행 큐의 구체적 내부 형태. 위 구조는 설계 방향이며 이러한 세부 결정은 검증이 필요하다.

구현은 2026-10-30 시작했다. 위 항목의 세부 선택과 검증 결과를 구현 기록에 남기며, 절대 성능 예산은 성공하는 SPA 기준선 확보 후 결정한다.
